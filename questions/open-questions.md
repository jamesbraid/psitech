# Open questions

Questions the shipped software and published sources have not yet answered. One entry each: the question, every route already tried, and the next route. When an entry is answered, move the finding into the owning page and delete the entry. `AGENTS.md` section 5 gives the rules.

1. **Board-control register effects and reset state.** What bits 1 and 5 do physically, whether the status in bit 5 is gated by bit 1 or only the interrupt is, bit 7's electrical meaning (it follows the keyboard and mouse controller's interrupt mask), and the reset value. Tried: driver use in full (set and clear around mode programming, DMA and frame waits; the handler reads bit 5 through a stored pointer and clears bit 1 when it is set), a constant scan of the standalone server and the refresh daemon for the offset (none, because they reach it through the driver). New: the RAD4-KM expansion ROM's keyboard read polls bit 4 ([software/firmware/rad4-option-rom.md](../software/firmware/rad4-option-rom.md#command-2-the-rad4-km-keyboard)); its meaning is unknown. Next: none in software beyond the buffered server's call sites, which the server page covers. Route: hardware only.
2. **Mailbox power-on value.** The driver skips its setup when mailbox word 0 is nonzero, reads words 1 and 2 as the keyboard and mouse device codes the firmware found, and writes word 0 to zero at the end of every attach. The producer and the caller are settled: the PsiTech PROM copies the option ROM into node memory and its later console install calls the ROM's initialiser, which writes `0x424f4f21` to word 0 once the console is up ([software/firmware/psitech-ip27-prom.md](../software/firmware/psitech-ip27-prom.md), [software/firmware/rad4-option-rom.md](../software/firmware/rad4-option-rom.md#command-0-initialisation)). The shipped serial EEPROM image loads zero into mailbox words 0 and 1 at reset ([software/rad4/proms-and-kernel.md](../software/rad4/proms-and-kernel.md#36500202-the-serial-eprom-image)), so a card carrying that image starts with word 0 at zero (established for the image, inferred for a card). Still unknown: word 2, which the part's EEPROM load does not cover, and what a card with another EEPROM image or none holds. Tried: the whole attach path, the ROM's writes, the serial EEPROM image decoded against the PLX load table. Next: none in software. Route: hardware only.
3. **Timing bank depths and what the timing bits do in hardware.** The bit rules of the timing words are established from both loaders (the driver's and the option ROM's, identical) and named by a comparison with VESA timings ([devices/rad4/modes.md](../devices/rad4/modes.md#timing-words)). Not decided: how many words each bank holds (the loaders need 781 horizontal and 1656 vertical) and what the board does with each bit. Unknown: no shipped software or published source depends on them. Tried: both loaders in full, the mode table, the register map's 4 KiB bank spacing, the RGB561 specification. Route: hardware only.
4. **Option fields on the board.** What horizontal and vertical polarity and the sync-type selector do electrically, and what selector 3 does. Tried: `rad4setres` usage text and mode routine. Next: nothing in software; unknown unless a board document turns up. Route: missing release or binary.
5. **Mask bit to plane mapping.** The driver's order is read: in the buffered path the mask is set before a DMA upload, written as all ones only around descriptor stores, and restored after the transfer has finished, which is what the driver relies on for the mask to reach DMA data (inferred; [devices/rad4/xserver-decode.md](../devices/rad4/xserver-decode.md#dma)). The server's masks are `0x0fffffff` at start-up, `0x00ffffff`, `0x0f000000` and, through the fill request, `0xf0000000`. Which mask bit reaches which board plane is unknown: the software only divides the word into colour, overlay and window-type groups, and no shipped software or published source depends on a finer mapping. Tried: the whole mask use of the driver and the server's GC validation and window-type paints. Route: hardware only.
6. **Plane and window-ID wiring.** How the 32-bit pixel word reaches the RAMDAC's pixel, overlay and window-ID inputs. The software side is read: every window attribute request carries mask `0xf`, so no shipped server code distinguishes IDs by bits 27 to 24, and the RAD GL libraries never reach the driver ([software/rad4/xserver-paths.md](../software/rad4/xserver-paths.md#33-window-id-bytes-established)). Unknown: whether the board wires bits 27 to 24 to both the overlay input and the low window-ID bits; no shipped software or published source depends on it. Tried: server visuals, the RGB561 window attribute table decode, every request-building site of the server and the libraries' strings. Route: hardware only.
7. **PCI configuration of a real card.** Subsystem IDs and the values a real card returns. The shipped serial EEPROM image declares class `0x038000`, revision 2, a 16 MiB BAR2 and an 8 MiB expansion ROM ([software/rad4/proms-and-kernel.md](../software/rad4/proms-and-kernel.md#36500202-the-serial-eprom-image)); that is what the image asks the part to claim, not a captured configuration, and the image is the RAD4-KM's. Tried: driver configuration reads, owner's guide installation example (gives IDs only), the ROM's PCI data structures and the EEPROM image. Next: other published `hinv -vm` or PCI listings that show the card. Route: missing release or binary.
8. **RAD4-KM controller part.** The register map is in defs form and the driver's use of it is read through initialisation, transmit, receive, the interrupt handler and the terminal's keyboard and pointer paths (see [devices/rad4/km-controller.md](../devices/rad4/km-controller.md) and [software/rad4/kernel-driver.md](../software/rad4/kernel-driver.md#keyboard-pointer-and-escape-sequences)). Unknown: the part number, the wiring of its output port bits and the interrupt routing; no shipped software or published source depends on them. Tried: the whole controller path, the option ROM's keyboard read (bit 4 of board control, which no driver path reads), the SCC68681 data sheet. Route: hardware only.
9. **Frame rate.** Whether the label, the clock-derived rate or something else is the physical refresh. Tried: clock arithmetic (differs from the label by up to 0.6 Hz). Next: none in software. Route: hardware only.
11. **Flash part number.** The 64 KiB flash with 128-byte sectors at BAR2 plus 0x800000 holds the package's ROM image (the programming tool writes it there) and the expansion ROM base register decodes it: the shipped serial EEPROM image re-maps the 8 MiB expansion ROM window to local address `0x800000` ([software/rad4/proms-and-kernel.md](../software/rad4/proms-and-kernel.md#36500202-the-serial-eprom-image)). Unknown: the part number; the geometry and the 0xaa, 0x55, 0xa0 unlock fit an AT29C512, and no data sheet for it is held. Tried: the driver's flash routines in full, the programming tool, the header, the serial EEPROM image. Route: missing release or binary.
12. **RAD1 PCI configuration and chip.** Which chip a shipped RAD1 carried (`104c:3d07` or `3d3d:0009`), its revision, class code, BAR sizes and subsystem pair as declared. Tried: the kernel driver's two registrations and its configuration reads (vendor, device, revision; it never writes configuration space) and the PROM's one-row table and subsystem test (`12d1:0101`), the product sheet text (does not name the chip), Usenet. Next: published `hinv -vm` or PCI listings of a RAD1, the archived RAD1 product page and users manual. Route: missing release or binary.
13. **PsiTech's RAD1 software.** The Graphics Server (the X server and DDX), the PsiTech PCI drivers and the CD. Tried: the held IRIX media and release notes, the Library's mail archives, the project's earlier searches of the web archives. Next: archived copies of PsiTech's download pages, patch and Supportfolio listings, any CD image sharing site; if the RAD4 server is the base, its request set is already a subset of what the stock driver serves. Route: missing release or binary.
14. **RAD1 resources and flash.** Which BAR the kernel's window 2 is, which BAR holds the framebuffer, and the flash part. Tried: both drivers' resource requests (the kernel's selectors are 8, 9 and 10 for windows 0 to 2 in every build from 6.5.4 to 6.5.30; whether window n is BAR n was not checked against a header) (the PROM uses the expansion ROM register for the flash) and the public Linux driver's BAR use. Next: public Permedia 2 board BAR layouts, a configuration dump. Route: missing release or binary.
15. **RAD1 flash contents.** What a new card holds, and so the mode it starts in. Tried: the mode word layout and the loader. Next: none in software. Route: hardware only.
17. **Video clock control at power-on.** The kernel reads it at attach as "the console already ran"; the value a real chip holds after reset is unknown. Tried: both drivers' use. Next: the TI TVP4020 manuals' reset-value tables, which were not read. Route: missing release or binary.
18. **Interrupt flag sources and bit meanings.** Bits 0, 1 and 7 are the only ones tested; the manual's bit table was not read, so the sources are inferred from use. Next: the TI manuals' interrupt sections. Route: missing release or binary.
20. **Mode order: header against table.** The shipped header gives 1280 by 1024 index 0 the 72 Hz label and index 1 the 60 Hz label, the opposite of the driver's table. Tried: the table, the tool, the header. Next: nothing in software; unknown which a real card's EEPROM follows. Route: hardware only.
21. **Board count.** The owner's guide change list says release 1.3 raised the number of RAD4 boards to 16; the 1.3k driver refuses a fifth. Tried: the attach count check. Next: compare an earlier driver release if one turns up. Route: missing release or binary.
22. **Terminal escape handlers beyond `A`, `H` and `f`.** The escape sequence table, key translation and the serial helpers are read ([software/rad4/kernel-driver.md](../software/rad4/kernel-driver.md#keyboard-pointer-and-escape-sequences)); the handlers for `J`, `K`, `g`, `h`, `l`, `m`, `r` and the unread branches of `rad4_read_tty` are classified by their final bytes only. Tried: Ghidra and listing readings of the dispatcher, `A`, `H` and `f`. Next: read those handlers. Route: software now.
23. **The `12d1:0100` board.** The PsiTech PROM has a case for it beside the RAD1, RAD4 and RAD4-KM, in both its boot stage and its console install. Tried: every PsiTech and SGI image held, the owner's guide, the product sheets. Next: none in software; unknown whether it is a product, a prototype or a placeholder. Route: missing release or binary.
27. **Source of the GLX configuration table behind the `GLoverlay_vid` writer.** The standalone server's GLX screen set-up writes the array when a configuration entry has a positive level and a class that matches an unclaimed visual ([software/rad4/xserver-paths.md](../software/rad4/xserver-paths.md#43-the-overlay-visual-and-what-is-undecided)). Not traced: where the table comes from and whether the shipped GL libraries' tables contain such an entry. Next: follow the caller of the GLX screen initialiser back to the table's producer. Route: software now.
