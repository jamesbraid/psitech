# Open questions

Questions the shipped software and published sources have not yet answered. One entry each: the question, every route already tried, and the next route. When an entry is answered, move the finding into the owning page and delete the entry. `AGENTS.md` section 5 gives the rules.

1. **Board-control register effects and reset state.** What bits 1 and 5 do physically, whether the status in bit 5 is gated by bit 1 or only the interrupt is, bit 7's electrical meaning (it follows the keyboard and mouse controller's interrupt mask), and the reset value. Tried: driver use in full (set and clear around mode programming, DMA and frame waits; the handler reads bit 5 through a stored pointer and clears bit 1 when it is set), a constant scan of the standalone server and the refresh daemon for the offset (none, because they reach it through the driver). New: the RAD4-KM expansion ROM's keyboard read polls bit 4 ([software/firmware/rad4-option-rom.md](../software/firmware/rad4-option-rom.md#command-2-the-rad4-km-keyboard)); its meaning is unknown. Next: none in software beyond the buffered server's call sites, which the server page covers.
2. **Mailbox power-on value.** The driver skips its setup when mailbox word 0 is nonzero, reads words 1 and 2 as the keyboard and mouse device codes the firmware found, and writes word 0 to zero at the end of every attach. The producer and the caller are settled: the PsiTech PROM copies the option ROM into node memory and its later console install calls the ROM's initialiser, which writes `0x424f4f21` to word 0 once the console is up ([software/firmware/psitech-ip27-prom.md](../software/firmware/psitech-ip27-prom.md), [software/firmware/rad4-option-rom.md](../software/firmware/rad4-option-rom.md#command-0-initialisation)). What a card holds before any firmware has run is not. Tried: the whole attach path, the ROM's writes. Next: none in software.
3. **Timing word bit meanings and bank depths.** The mode loaders write per-mode words; nothing public describes them. Tried: both loaders (lengths and word contents derived for all 13 modes and eight option combinations), the RGB561 specification. Next: compare the words with VESA-style timings per mode to name the fields (parameters 2 and 3 are inferred as sync start and end from blanking start).
4. **Option fields on the board.** What horizontal and vertical polarity and the sync-type selector do electrically, and what selector 3 does. Tried: `rad4setres` usage text and mode routine. Next: nothing in software; unknown unless a board document turns up.
5. **Mask bit to plane mapping.** Which write-mask bits reach which board plane, and whether the mask reaches DMA. Tried: driver mask use, server GC validation (masks `0x00ffffff` and `0x0f000000`). Next: the driver's DMA path ordering against the mask restore.
6. **Plane and window-ID wiring.** How the 32-bit pixel word reaches the RAMDAC's pixel, overlay and window-ID inputs. Tried: server visuals and RGB561 window attribute table decode. Next: check whether any shipped code depends on bits 27 to 24 of the window ID.
7. **PCI configuration of a real card.** Revision, subsystem IDs and BAR sizes (the class code is `0x038000` in both PCI ROM images and the shipped serial EEPROM image agrees). Tried: driver configuration reads, owner's guide installation example (gives IDs only), the ROM's PCI data structures and the EEPROM image. Next: other published `hinv -vm` or PCI listings that show the card.
8. **RAD4-KM controller part.** The register map is in defs form and the driver's use of it is read through initialisation, transmit, receive and the interrupt handler (see [devices/rad4/km-controller.md](../devices/rad4/km-controller.md)). Still open: the part number and the wiring of its output port bits, the interrupt routing, and the terminal's scan code translation and the keyboard and pointer read paths, which were not decoded. Tried: the whole controller path, the SCC68681 datasheet. Next: decode `translate_key`, `key_handler` and the serial read and write helpers.
9. **Frame rate.** Whether the label, the clock-derived rate or something else is the physical refresh. Tried: clock arithmetic (differs from the label by up to 0.6 Hz). Next: none in software.
10. **Buffered and multi-device server modes.** The dispatcher's device type 3 branches and the buffered server's drawing paths. Tried: the DMA submission path. Next: trace the type 3 branch of each request.
11. **Expansion ROM content and the flash.** The driver enables the expansion ROM base register and reaches DMA registers through the 8 MiB resource; a separate 64 KiB flash with 128-byte sectors sits at BAR2 plus 0x800000. Open: whether the expansion ROM base register decodes any ROM image at all (the flash is a candidate for what holds the package's ROM image) and the flash part number. Tried: the driver's flash routines in full, the 8 MiB window request. New: the PsiTech PROM reads the ROM image through the expansion ROM base register and runs it, so the register decodes the programmed image (inferred; [software/firmware/psitech-ip27-prom.md](../software/firmware/psitech-ip27-prom.md)). Next: the programming tool's use of requests 129 and 130, covered on the firmware page.
12. **RAD1 PCI configuration and chip.** Which chip a shipped RAD1 carried (`104c:3d07` or `3d3d:0009`), its revision, class code, BAR sizes and subsystem pair as declared. Tried: the kernel driver's two registrations and the PROM's one-row table and subsystem test (`12d1:0101`), the product sheet text (does not name the chip), Usenet. Next: published `hinv -vm` or PCI listings of a RAD1, the archived RAD1 product page and users manual.
13. **PsiTech's RAD1 software.** The Graphics Server (the X server and DDX), the PsiTech PCI drivers and the CD. Tried: the held IRIX media and release notes, the Library's mail archives, the project's earlier searches of the web archives. Next: archived copies of PsiTech's download pages, patch and Supportfolio listings, any CD image sharing site; if the RAD4 server is the base, its request set is already a subset of what the stock driver serves.
14. **RAD1 resources and flash.** Which BAR the kernel's window 2 is, which BAR holds the framebuffer, and the flash part. Tried: both drivers' resource requests (the PROM uses the expansion ROM register for the flash) and the public Linux driver's BAR use. Next: public Permedia 2 board BAR layouts, a configuration dump.
15. **RAD1 flash contents.** What a new card holds, and so the mode it starts in. Tried: the mode word layout and the loader. Next: none in software.
16. **First kernel release with the RAD1 driver.** The console code is pinned: the first IO6 and IP27 PROMs with it are both 6.27, built 18 Mar 1999 ([software/firmware/sgi-prom-rad1.md](../software/firmware/sgi-prom-rad1.md#release-history)). The first IRIX release carrying the kernel driver is not. Tried: media listings (driver absent from the June 1998 6.5 media, present in 6.5.30), a 6.5.4 maintenance build target list. Next: any 6.5.x overlay or patch media between them that lists `rad1pci.a`.
17. **Video clock control at power-on.** The kernel reads it at attach as "the console already ran"; the value a real chip holds after reset is unknown. Tried: both drivers' use. Next: the TI TVP4020 manuals' reset-value tables, which were not read.
18. **Interrupt flag sources and bit meanings.** Bits 0, 1 and 7 are the only ones tested; the manual's bit table was not read, so the sources are inferred from use. Next: the TI manuals' interrupt sections.
19. **Local bus region descriptor bits around DMA and the interrupt handler.** The driver rewrites BAR0 offset 0x18 in three places: it sets bit 19 and clears bit 22 for a DMA, flips them back afterwards, and the interrupt handler ORs in 0x400300 over a mask. Tried: the three functions in full; the mask constant was not resolved from the decompilation. Next: read the mask from the object's constant data and match the bits against the PLX bus region descriptor table.
20. **Mode order: header against table.** The shipped header gives 1280 by 1024 index 0 the 72 Hz label and index 1 the 60 Hz label, the opposite of the driver's table. Tried: the table, the tool, the header. Next: nothing in software; unknown which a real card's EEPROM follows.
21. **Board count.** The owner's guide change list says release 1.3 raised the number of RAD4 boards to 16; the 1.3k driver refuses a fifth. Tried: the attach count check. Next: compare an earlier driver release if one turns up.
22. **Terminal and early textport code paths.** The driver's escape sequence table, key translation and the buffer helpers behind `rad4_read_tty` and `rad4_write_serial` are not decoded. Next: Ghidra readings of those functions.
23. **The `12d1:0100` board.** The PsiTech PROM has a case for it beside the RAD1, RAD4 and RAD4-KM, in both its boot stage and its console install. Tried: every PsiTech and SGI image held, the owner's guide, the product sheets. Next: none in software; unknown whether it is a product, a prototype or a placeholder.
24. **How the Origin 300 PROM names PsiTech devices.** `PSITECH` and `PSITECH_RAD1` are in diagnostic name tables of every IP35 PROM since 6.81 but no routine the decompiler found references them. Tried: constant scans and pointer scans of the 6.210 image. Next: read the I/O configuration test's name lookup by hand, starting at the "Device %d Type %s" message.
25. **The RAD1 PROM's mode table.** [software/rad1/textport.md](../software/rad1/textport.md) gives three records for the PROM's index limit; the IO6 PROM 6.156 holds eight records and an index limit of 8 ([software/firmware/sgi-prom-rad1.md](../software/firmware/sgi-prom-rad1.md#the-start-up-mode-record)). Tried: the table and the compare read in the PROM. Next: the owner of the RAD1 pages to reconcile; the last record's final word overlaps the limit word in the image, which may be how the three came out.
26. **The expansion ROM's mode and timing routines.** Command 0 reaches a mode routine, two timing loaders and a fill helper through the relocated pointer table (slots at image offsets 0x4c to 0x6c); only the RAMDAC initialiser was read. Tried: the initialisation sequence around them, the mode table (identical to the driver's). Next: read the routines the table names and compare their stores with [devices/rad4/modes.md](../devices/rad4/modes.md#mode-programming-sequence).
27. **`GLoverlay_vid` writer.** The standalone X server compares every overlay test against `GLoverlay_vid`, which is -1 in the binary, and no store to it was found in the server, the DDX module or the GL libraries, so the overlay behaviours in devices/rad4/xserver-decode.md (colour rewriting, overlay clear on window moves) may not be reached by the standalone server on its own. Tried: a scan for stores through computed addresses (see software/rad4/xserver-paths.md). Next: look at what the GL libraries set at run time; the observed emulator run did show those paths executing, so a writer exists outside the scanned code.
