# Open questions

Questions the shipped software and published sources have not yet answered. One entry each: the question, every route already tried, and the next route. When an entry is answered, move the finding into the owning page and delete the entry. `AGENTS.md` section 5 gives the rules.

1. **Board-control register effects and reset state.** What bits 1 and 5 do physically, whether the status in bit 5 is gated by bit 1 or only the interrupt is, bit 7's electrical meaning (it follows the keyboard and mouse controller's interrupt mask), and the reset value. Tried: driver use in full (set and clear around mode programming, DMA and frame waits; the handler reads bit 5 through a stored pointer and clears bit 1 when it is set), a constant scan of the standalone server and the refresh daemon for the offset (none, because they reach it through the driver). Next: none in software beyond the buffered server's call sites, which the server page covers.
2. **Mailbox power-on value and producer.** The driver skips its setup when mailbox word 0 is nonzero, reads words 1 and 2 as the keyboard and mouse device codes the firmware found, and writes word 0 to zero at the end of every attach. Tried: the whole attach path. The package's option ROM image writes the marker 0x424f4f21 to it (software expectation, [proms-and-kernel](../software/rad4/proms-and-kernel.md)). Next: who calls that image: the PsiTech PROM copies and relocates it but was not seen calling it.
3. **Timing word bit meanings and bank depths.** The mode loaders write per-mode words; nothing public describes them. Tried: both loaders (lengths and word contents derived for all 13 modes and eight option combinations), the RGB561 specification. Next: compare the words with VESA-style timings per mode to name the fields (parameters 2 and 3 are inferred as sync start and end from blanking start).
4. **Option fields on the board.** What horizontal and vertical polarity and the sync-type selector do electrically, and what selector 3 does. Tried: `rad4setres` usage text and mode routine. Next: nothing in software; unknown unless a board document turns up.
5. **Mask bit to plane mapping.** Which write-mask bits reach which board plane, and whether the mask reaches DMA. Tried: driver mask use, server GC validation (masks `0x00ffffff` and `0x0f000000`). Next: the driver's DMA path ordering against the mask restore.
6. **Plane and window-ID wiring.** How the 32-bit pixel word reaches the RAMDAC's pixel, overlay and window-ID inputs. Tried: server visuals and RGB561 window attribute table decode. Next: check whether any shipped code depends on bits 27 to 24 of the window ID.
7. **PCI configuration of a real card.** Revision, class code, subsystem IDs and BAR sizes. Tried: driver configuration reads, owner's guide installation example (gives IDs only). Next: other published `hinv -vm` or PCI listings that show the card.
8. **RAD4-KM controller part.** The register map is in defs form and the driver's use of it is read through initialisation, transmit, receive and the interrupt handler (see [devices/rad4/km-controller.md](../devices/rad4/km-controller.md)). Still open: the part number and the wiring of its output port bits, the interrupt routing, and the terminal's scan code translation and the keyboard and pointer read paths, which were not decoded. Tried: the whole controller path, the SCC68681 datasheet. Next: decode `translate_key`, `key_handler` and the serial read and write helpers.
9. **Frame rate.** Whether the label, the clock-derived rate or something else is the physical refresh. Tried: clock arithmetic (differs from the label by up to 0.6 Hz). Next: none in software.
10. **Buffered and multi-device server modes.** The dispatcher's device type 3 branches and the buffered server's drawing paths. Tried: the DMA submission path. Next: trace the type 3 branch of each request.
11. **Expansion ROM content and the flash.** The driver enables the expansion ROM base register and reaches DMA registers through the 8 MiB resource; a separate 64 KiB flash with 128-byte sectors sits at BAR2 plus 0x800000. Open: whether the expansion ROM base register decodes any ROM image at all (the flash is a candidate for what holds the package's ROM image) and the flash part number. Tried: the driver's flash routines in full, the 8 MiB window request. Next: the programming tool's use of requests 129 and 130, covered on the firmware page.
12. **RAD1 PCI configuration and chip.** Which chip a shipped RAD1 carried (`104c:3d07` or `3d3d:0009`), its revision, class code, BAR sizes and subsystem pair as declared. Tried: the kernel driver's two registrations and the PROM's one-row table and subsystem test (`12d1:0101`), the product sheet text (does not name the chip), Usenet. Next: published `hinv -vm` or PCI listings of a RAD1, the archived RAD1 product page and users manual.
13. **PsiTech's RAD1 software.** The Graphics Server (the X server and DDX), the PsiTech PCI drivers and the CD. Tried: the held IRIX media and release notes, the Library's mail archives, the project's earlier searches of the web archives. Next: archived copies of PsiTech's download pages, patch and Supportfolio listings, any CD image sharing site; if the RAD4 server is the base, its request set is already a subset of what the stock driver serves.
14. **RAD1 resources and flash.** Which BAR the kernel's window 2 is, which BAR holds the framebuffer, and the flash part. Tried: both drivers' resource requests (the PROM uses the expansion ROM register for the flash) and the public Linux driver's BAR use. Next: public Permedia 2 board BAR layouts, a configuration dump.
15. **RAD1 flash contents.** What a new card holds, and so the mode it starts in. Tried: the mode word layout and the loader. Next: none in software.
16. **First releases with RAD1 support.** The first IRIX and IO6 PROM release that carry the driver and the console code. Tried: media listings (driver absent from the June 1998 6.5 media, present in 6.5.30), PROM 6.11 (no console code) and 6.156 (present), a 6.5.4 maintenance build target list. Next: scan the other catalogued IO6 PROM images (6.12 to 6.139) and the 6.5.x overlays for the console strings.
17. **Video clock control at power-on.** The kernel reads it at attach as "the console already ran"; the value a real chip holds after reset is unknown. Tried: both drivers' use. Next: the TI TVP4020 manuals' reset-value tables, which were not read.
18. **Interrupt flag sources and bit meanings.** Bits 0, 1 and 7 are the only ones tested; the manual's bit table was not read, so the sources are inferred from use. Next: the TI manuals' interrupt sections.
19. **Local bus region descriptor bits around DMA and the interrupt handler.** The driver rewrites BAR0 offset 0x18 in three places: it sets bit 19 and clears bit 22 for a DMA, flips them back afterwards, and the interrupt handler ORs in 0x400300 over a mask. Tried: the three functions in full; the mask constant was not resolved from the decompilation. Next: read the mask from the object's constant data and match the bits against the PLX bus region descriptor table.
20. **Mode order: header against table.** The shipped header gives 1280 by 1024 index 0 the 72 Hz label and index 1 the 60 Hz label, the opposite of the driver's table. Tried: the table, the tool, the header. Next: nothing in software; unknown which a real card's EEPROM follows.
21. **Board count.** The owner's guide change list says release 1.3 raised the number of RAD4 boards to 16; the 1.3k driver refuses a fifth. Tried: the attach count check. Next: compare an earlier driver release if one turns up.
22. **Terminal and early textport code paths.** The driver's escape sequence table, key translation and the buffer helpers behind `rad4_read_tty` and `rad4_write_serial` are not decoded. Next: Ghidra readings of those functions.
